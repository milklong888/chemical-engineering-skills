# 后台运行与计算说明

## 从资料到结果

完整流程如何从骨架走到切岛、接回和验收，见[全流程工作原理](全流程工作原理.md)。
这里进一步解释程序内部怎样接收数据、计算和返回证据。

技能集有三个不同的工作对象：设计要求、知识依据和当前工程数据。设计要求先
确定要做什么、允许怎么做；知识库提供相关原理和适用方法；当前模型导出提供
这次真正要计算的流量、组成、温压和负荷。三者不混成一份“模型记忆”。

`tools/expert_cli.py` 是无界面统一入口，通过一个驻留调用层执行
`backends/equipment/app/equipment_design_agent.py` 的原 JSON 接口。原程序先
归一单位、识别设备族、执行可闭合的公式、建立参数包，再按已登记规则给出型式
和规格层级。结果包含直接值、推导值、估算值、公式链及未闭合项，随后才进入
`backends/process/feedback.py` 判断是否需要改动流程。

统一入口可直接发现原协议和字段，开放18项本地操作：能力与字段查询、目录与
标准检索、单台和批量匹配、已有导出推导、报告及客户表输出、PFD数据操作，
以及模型辅助建议的本地准备、校核和批准应用。模型辅助并不意味着该工具
必须连接另一个模型服务；调用宿主可处理已冻结的资料，再交程序验证建议。
远程模型执行和真实Aspen导入是明确隔离的可选路径。

在建模阶段，`design_stage`不是返回一个“建议调用”的模块列表便结束。
`tools/design_stage.py`通过同一入口实际查询知识并逐项执行设备请求，条件
具备时复用反馈与复算核验；请求、结果和缺口都进入阶段收据。某项计算失败
不会抹掉其余结果，缺少设备输入的资料阶段也不会捏造设备数值。收据不等于
已读懂原文、设备清单完整或工程通过，这些仍由对应专业工作流检验。

例如合成换热器测试给出 1000 kW、U=500 W/(m²·K)、对数平均温差 40 K、修正
系数1。程序先把负荷换为 W，再计算 `A=Q/(U·F·ΔTlm)=50 m²`。这一步是给定
输入下的面积计算，不包含污垢、两侧压降、振动、热应力或制造校核。若没有管径、
管长、流路与内件资料，程序仍应返回50 m²及其依据，同时列出后续所缺资料；
不能把缺少机械证据说成面积也无法算，更不能把50 m²包装成完整设备设计。

## 求解分类与实际软件执行

`tools/aspen_tool_router.py` 是一个小型方法路由器，统一入口用 `solve_route`
调用，阶段入口也复用它。它接受当前问题和明确的意图分类，返回推荐工具、
插入时机、需要的项目输入、证据和实际参考文件路径。内置词面规则只给有限提示，
未识别时由 Agent 继续分类，不会自动认定“不适用”。

这个路由器不求解方程、不改模型、不启动 Aspen，也不把文件哈希或自报状态
当作原生执行证明。读值、Calculator、Sensitivity、Design Spec/Vary、
Optimization 和回归的实际操作仍归公共操作层。外部替代理由及引用即使完整，
也只进入专业审查，不能靠填一个 reason 字段获得豁免。

原生分析与外部循环的区别看实际对象和结果，不看函数名称。随包 Aspen MCP 的
`sensitivity` 会在外部逐点修改输入、运行和读值；它的比例联动不代替内层目标
求解。真正原生分析要核对当前模型中保留的分析定义、变量与单位、结果表/残差
和同案下游状态。如此，工具路由、软件执行和工程判断各自有明确责任。

## 知识库为什么分层

`knowledge/records.jsonl` 保存原节点内容及来源标识。上层是守恒、驱动力、
尺度、系统耦合和能量品位等判断原则，中层是机制和方法，下层是操作细节及
来源定位。查询先限制资料范围和证据资格，再排序；高层设计问题优先返回概念，
不会仅因某页公式多、关键词密而让它支配方案。

`knowledge/scripts/query_knowledge.py` 可在没有原PDF的情况下查询随包正文。
原页未再分发、整页OCR被排除或表达待审查时，记录会明确区分“身份已知”和
“正文可用”。命中一个源节点只说明找到了依据，不证明其数值可用于当前工程。

设备标准事实在 `backends/equipment/data/standard_facts.sqlite.gz`。它保留
24,887 条标准记录和1,844条图记录，以及来源标准、版本、页表单元格、单位、
条件、关系、原QA状态和原记录hash。运行时先核验压缩文件与解压内容身份，再
在内存载入SQLite；无需打开扫描页或回读旧电脑的目录。

这个库没有把所有记录都提升为计算依据。当前原管路消费者直接使用的限定集合
是12条PN与5,620条尺寸记录；这些输出字段与原库逐项比较。其余事实可供检索，
但仍需选择适用公式和核对工程条件。`METHOD_ONLY`、厂家边界、待核或旧版本
标记保留原意，不会因为进了数据库就成为可采购的规格。

## 设备选不出时，程序怎样分辨原因

首先保留原计算结果，再分别检查单位/基准、物理约束、能力上限、目录覆盖和
正式证据缺口。目录没有型号，并不能推出设备太大；缺少厂家曲线，也不等于
已有的物料衡算和功率计算作废。

反馈候选要求明确的超限记录：当前设备ID、比较量、单位、最大或最小界限、
适用性审查，以及实际值和界限值各自的文件hash与JSON定位。程序重新读取这些
文件并计算比较结果，不能只接受一个 `exceeded=true`。适用性判断本身仍由
引用的工程资料和审查负责；hash只解决“是不是同一份依据”。

输入连接采用明确的 `equipment-process-canonical-export-v1`，不是猜测任意
Aspen导出结构。每个设备包含当前case/run、设备族、values和units；当前要求
用 `equipment-process-authority-v1` 记录。程序逐值对照选型器实际归一输入，
不让旧工况或另一设备的数据通过。限制文件使用 `equipment-process-limit-v1`，
同时给出量纲、来源版本、定位和适用设备。面积等本次推导量可以引用
`current_selector_derivation`，直接使用本次原计算轨迹，不要求用户重复抄数。
缺少这项绑定时保留计算结果，只阻止该设备的改造实施结论。

在这些条件满足后，优先生成换热器串联、压缩机串联分级、塔并联的评审候选。
程序不凭一个面积或压比就替工程师固定台数。

换热器串联要逐段求进出口状态。相邻段连续，后一段接收前一段真实出口；两侧
温差、相变段和U可能变化，面积不能平均分。串联仍承受相同通过流量，而且增加
总压降，所以流速超限或压降超限不能靠机械增加串联台数解决。EDR 总表只能
证明整体结果；逐壳结果应读取 `Shell by Shell Conditions` 的进出口温压、
气相质量分数及热负荷。[AspenTech 逐壳结果说明](https://esupport.aspentech.com/S_Article?id=000098247)。

压缩机分级要把级间冷却器、分离器和管路损失扣除后，才得到下一段吸入压力。
`equal_ratio_initializer` 解出包含显式损失的相同级压比初值，不把它称为最优。
`compressor_train` 在使用者明确采用理想气体、恒定比热的初筛近似时，计算
各段排温、气体功和级间需要移走的热量；若指定的下一段入口更热，则明确输出
需要加热。实际气体物性、湿压缩、轴系效率和厂家运行包络需另按同工况验证。

塔并联是分流量，而不是把所需理论级数分给几座塔。各列要独立满足分离要求，
再检查产品混合后的总规格。`parallel_distribution` 使用各支路有来源的
流量—压差曲线求共同压差与流量分配，不外推。合成例中A、B在同一10 kPa压差
下分别通过20与10 m³/h，总量30 m³/h；并联系统压差仍为10 kPa，不是20 kPa。
曲线只是输入模型，塔内件评级、进出口组成与控制稳定性仍要单独检查。

## 压降计算的具体边界

`backends/process/pressure.py` 的单相液体圆管计算采用：

```text
u = 4Q / (πD²)
Re = ρuD / μ
ΔP摩擦 = f_D (L/D) ρu²/2
ΔP局部 = ΣK ρu²/2
ΔP静压 = ρgΔz
Pin - Pout = ΔP摩擦 + ΔP局部 + ΔP静压
```

输入使用SI单位；这里的摩擦因子是Darcy因子，不是Fanning因子。低雷诺数层流
采用 `64/Re`；过渡或湍流需要调用方给出有依据的因子。程序不暗设粗糙度、
管件K值或允许压降。静压可能因下降而为负，摩擦损失始终非负，两者分别输出。
此式限定常密度、相同进出口面积的单相牛顿液体；不能直接套给大压降气体或
两相流。[EPA EPANET 方法范围](https://www.epa.gov/water-research/epanet)。

换热器需壳程/管程各自几何和关联式或EDR结果；塔需塔板/填料、气液负荷与
对应水力学方法。面积、塔径或一次物料模拟通过，都不能单独推出完整压降。
串联可组合各段已经得到的损失，但热态改变后必须重新计算段内损失。

## 怎样把结果返回流程

反馈计划保存原导出、设计要求、原设备响应及其hash。增加或改动设备后，相关
上下游和循环可能都受影响，因此程序把声明拓扑中的整个连通部分标为待复算。
没有完整拓扑时只返回局部覆盖状态，不声称找全受影响设备。

专业建模技能根据已批准变更，在受保护模型副本上实施新连接和输入，再由真实
软件重算。外部脚本只能写卡片、调度和审计，不能把自己的计算出口塞回模型，
再称其为Aspen求解结果。随后从新模型重新导出并再次选型，旧设备参数包失效。

`replay_audit` 将模型文件、导出、计划和各专业验收回执绑到同一版，逐个检查
文件是否还存在且未漂移。一个 `passed=true` 不够，回执须包含校核方法、具体
检查与可回读证据。它证明的是证据链连续，不独立证明每个专业计算正确；
`engineering_accepted` 不会被这个登记程序自动置为真。

当前程序已实际接入的专业回执复核是Aspen严格Run Status：重新读取有hash的
Control Panel与HIS原始内容，调用既有 `aspen_evidence.py` 检查真实表头、全部
计数和实际诊断行。即使外层写着通过，HIS中仍有warning也不能通过。安装后使用
原字节的 `validators/aspen_evidence.py`，不回退到用户旧技能目录。

另外十项——原生拓扑、物料组分、能量、压力网络、相态与温差、产品、重新选型、
操作控制、安全材料、精确交付复开——仍由相应专业技能与真实模型证据完成；本
回执程序没有为它们捏造通用判定器，所以不能自动给出“全流程通过”。压力函数
能给出具体算式结果，但不等于整个压力网络已经校核。这样的状态会明确列出，
不会用文件存在或一个自报的布尔值代替工程工作。

## 哪些测试支持可靠性

设备后端测试对照原算法的17族结果、公式链和型式选择，另对管路数据逐字段
比较；缺库、数据变动、源码变动和未授权COM路径必须明确失败。压力与反馈
测试覆盖守恒、串并联差异、级间损失、错误来源hash、旧计划及缺回执。

MCP测试在新建依赖环境中进行真实握手和工具调用，监测网络与COM调用，结束后
确认自有子进程退出。这证明本地接口能工作，不证明Aspen模型已运行。知识查询
与依赖版本也有独立清单和测试；不存在一个以“全通过”替代所有工程验收的总分。
