# 使用手册

## 1. 用途与工作范围

把任务书、论文、参数表或已有模型交给这套Skill，可以从设计基准和路线审查开始，
逐步建立或修复Aspen流程，优化反应、分离、热泵与压力安排，并用设备计算检查
方案的可实现性。需要交付时，再把同版模型、计算依据、设备清单、流程图和报告
联系起来核验；已有工程从当前进度继续，单项任务只走相关模块。

完整建模的主线是“资料与方法确定—授权简化骨架—切岛严化与优化—逐个接回—
全流程复算与验收”。知识图谱在选择方法时提供适用依据，设备程序在骨架有负荷、
岛内工况确定以及接回后实际计算。设备约束要求改变方案时，结果返回工艺层，
而不是停在选型表。先阅读[全流程工作原理](全流程工作原理.md)即可了解这套配合，
各小Skill的具体过程见[模块说明](模块说明.md)。

技能文件规定工作方法，脚本执行具体操作。知识节点、设备后端和标准事实随完整
离线发行包提供；Aspen、EDR、SW6及未再分发的原始资料仍由使用环境提供。完整边界见
[外部资料与软件](外部依赖.md)。

## 2. 目录及职责

| 目录 | 职责 |
| --- | --- |
| `plugins/chemical-engineering-skills/skills/` | 专业技能。每个模块有独立`SKILL.md`入口及按需读取的参考文件。 |
| `plugins/chemical-engineering-skills/.codex-plugin/` | 插件身份、版本和技能目录声明。 |
| `workspace/` | 新工作区的公共路由、项目记录模板及本地检索工具。 |
| `tools/` | 统一CLI/MCP、阶段调用、设备调度、发布包检查、安装和隔离验证工具。 |
| `knowledge/` | 原理、方法与操作节点、来源与保全清单、离线查询工具。 |
| `backends/equipment/` | 原设备算法、结构化规则、标准事实数据库和无界面 JSON 接口。 |
| `backends/process/` | 设备诊断、串联/分级/并联候选、压降计算及同版复算追溯。 |
| `vendor/aspen-mcp-toolkit/` | 有许可的原 Aspen MCP 源码、独立离线启动器和依赖锁。 |
| `runtime/wheelhouse/` | 供目标环境离线安装的固定版本 Python 依赖。 |
| `docs/` | 使用方法、模块说明、文件索引、依赖和验证范围。 |

项目文件与技能文件分开保存。技能目录存放可重复使用的方法；项目工作区保存
本项目的资料、模型、参数、计算结果和审批记录。原始资料保留原件，计算及模拟
使用工作副本，交付文件另设目录。

## 3. 环境与安装

### 3.1 基本环境

完整离线运行路径在 CPython 3.14、Windows AMD64 下核验。Python 解释器由目标
电脑提供，MCP 和 NumPy 依赖由包内轮子安装。纯规则、基础查询与多数设备公式
不依赖远程 API。涉及 COM 的操作仍要求本机安装、许可和注册相应 Aspen 产品；
不能用库导入或协议握手代替商业软件验收。

未安装商业软件时，可以阅读规则、整理资料、编制参数和证据清单、进行通用
离线检查；不能据此宣称已完成真实模拟、EDR计算或机械设计验证。

### 3.2 安装前检查

从发行页下载压缩包和校验文件，解压到较短的可写路径。在解压后的仓库根目录运行：

```powershell
python tools/verify_release.py --root .
```

检查通过表示文件清单、哈希和规定结构相符。若文件缺失或被修改，先恢复正确
发行文件，不跳过校验继续安装。

建立独立的离线依赖环境；以下目标目录必须尚不存在：

```powershell
python tools/install_offline_runtime.py --wheelhouse runtime/wheelhouse --extension-lock vendor/aspen-mcp-toolkit/numpy-retrieval-extension.lock.json --extension-wheelhouse runtime/wheelhouse/extensions/numpy --target D:/ChemicalRuntime/python-env
```

安装器检查 Python 平台、每个依赖的版本和哈希，使用本地文件安装，再检查依赖
关系；不会自动下载、修改全局 Python 或复用一个安装失败的环境。之后用
`D:/ChemicalRuntime/python-env/Scripts/python.exe` 调用需要 MCP/NumPy 的工具。
纯设备计算与基础查询也可在该环境中统一执行。

### 3.3 安装到指定目录

先查看安装计划。以下目录只是示例，应替换为实际位置：

```powershell
python tools/install.py --workspace-root D:/ChemicalWork --skills-root "$env:USERPROFILE/.agents/skills" --dry-run
```

确认目标目录后执行：

```powershell
python tools/install.py --workspace-root D:/ChemicalWork --skills-root "$env:USERPROFILE/.agents/skills"
```

工作区宜使用新的空目录。默认安装不覆盖有冲突的已有文件；确需更新时，核对
影响范围后使用`--replace`，由安装器备份受影响文件。备份不放在技能自动发现
目录内。安装只处理本发行包列出的文件，不递归改写用户的其他项目资料。

文件中的`{CHEM_WORKSPACE}`和`{CHEM_SKILLS}`是安装定位标记，由安装器替换。
它们不是需要发给模型的提示词。安装完成后新开一个Codex任务，以重新加载技能。
Codex的技能与插件加载方式参见[官方技能说明](https://learn.chatgpt.com/docs/build-skills)。

安装器将后端、知识、工具及离线依赖按原字节放到工作区的
`chemical-engineering-runtime/`，保留它们内部的验证清单。直接在解压目录运行也
可以，不必为了查询资料先安装全部技能。

本包没有远程服务或后台自动任务。MCP 以本地子进程的标准输入输出通信，运行
`tools/expert_mcp.py` 可向兼容宿主提供知识查询、设备计算、压力计算、反馈计划和
复算回执核验。Aspen 的原 70 工具封装单独通过
`vendor/aspen-mcp-toolkit/run_offline_mcp.py` 启动；不自动连接模型。配置时填写
已建环境的 Python 路径和对应脚本绝对路径，不在命令中放令牌。插件机制参见
[官方插件说明](https://learn.chatgpt.com/docs/build-plugins)。

## 4. 新建工程任务

### 4.1 准备输入

开始前至少给出工作对象、目标、设计基准和资料位置。按任务提供相关内容：

| 输入类别 | 典型内容 |
| --- | --- |
| 工作对象 | 流程、工段、塔、换热器、压缩机或报告章节。 |
| 设计基准 | 处理量、组成、温压、操作周期、产品规格、物性及单位基准。 |
| 工作目标 | 新建、审查、优化、修复、设备校核、费用分析或文件交付。 |
| 方法要求 | 指定方法、资料优先级、适用标准、可调整变量和不能改变的条件。 |
| 现有成果 | 文档、参数表、模型文件、运行日志、设备计算或来源账本。 |
| 验收条件 | 数值指标、计算精度、软件版本、设备约束及交付文件类型。 |

缺少输入时，先检查能否由现有资料提取、换算或推导。仍缺失的变量应列明其
用途和影响，不把未确定的量混入正式结果。

### 4.2 选择主工作流

一般任务先由`chemical-engineering-expert`确定设计与证据边界，再选择一个
主要专业模块。建模任务通常进入`aspen-document-driven-flowsheet`；已有模型
故障进入`aspen-flowsheet-error-repair`；塔优化、热泵替换、EDR或设备选型分别
使用对应模块。具体文件入口见[模块说明](模块说明.md)。

操作层`aspen-plus-operations`负责卡片写入、运行、导出和结果读取。它接收已
确定的工程条件，不自行改变工艺路线、设计基准或产品目标。

### 4.3 保持项目记录

同一项目应有当前状态记录及变更表。变更表记录原始资料要求、当前采用方案、
变更原因、依据和允许继续执行的工作。一个关键参数或拓扑发生变化时，同时
列出受影响的物流、设备、循环、能量和报告内容，按依赖关系复核。

相应设计阶段须执行`design_stage`，保存真实查询和设备响应，并把收据路径
写入当前阶段记录。调用程序不代替对来源、方法、清单覆盖和软件结果的审查；
具体时机见[阶段调用规则](../plugins/chemical-engineering-skills/skills/chemical-engineering-expert/references/DESIGN_STAGE_ROUTING.md)。

## 5. 设计与计算顺序

### 5.1 先检查工艺结构

先判断反应与分离方法是否适用，物性方法和相态是否合理，物料与能量能否闭合，
压力路径及循环是否成立。随后检查产品与废物流去向、操作和控制、安全与环保
要求，以及设备能否实现拟定工况。

可行方案之间再进行同基准比较。评价可以包含能耗、设备规模、成本、可操作性
和复杂程度，但关键物理约束及验收条件不能用其他指标的改善抵消。

### 5.2 组织详细模型

把资料转成单位一致的参数及来源账本。允许简化时先搭连接完整的骨架，检查全部
新鲜进料、产品、废物流、压力和循环，再从最新导出冻结入口，切出反应或分离岛
逐段严化。塔、热泵、动力学等分别交给对应模块；岛通过局部检查后一次接回一个，
再核对新的全流程入口和循环。模型运行、参数改变及导出文件均记录对应版本，
避免不同候选之间混用产品、设备和费用结果。已有中段模型不重复这条路线的前半段。

反应动力学需要完整的来源、单位、换算、模型卡片及导出核对链。来源不足的
动力学模型只能处于待补充或临时状态。

### 5.3 校核设备并反馈流程

设备选型使用同一候选流程导出的负荷、温压、物性及组成。先完成可确定的计算，
再判断结构或型号适用性。资料缺失、目录覆盖不足与实际设备能力超限分别处理。

若确有能力限制，换热任务优先检查串联分段，压缩任务优先检查串联分级，塔优先
检查并联分流。这个次序不是万能拆分公式：串联换热器不降低通过流量，并联塔
不减少每列所需分离级数，级间损失也不能从压缩机计算里省略。选定方案后回到
真实流程重算压降、功耗、热量、循环、产品与费用。具体算法和计算边界见
[后台运行与计算说明](后台运行与计算说明.md)。

### 5.4 比较节能方案

节能分析先检查过程本身的热负荷和可回收热量，再比较温度层级调整及适用的
蒸汽再压缩或热泵方案。压缩功、端温差、排气状态、开停车、备用方式和经济基准
应与外供热量一起评价。

## 6. 结果状态与交付

读取到结果、操作执行完毕、求解无错误、达到产品指标和完成工程交付分别表示
不同状态。交付记录应说明具体通过了哪些检查、仍有哪些条件未验证。

Aspen文件按适用版本的完整错误汇总表和本次原始运行日志检查全部错误与警告；
随后核对本项目的产品、容量、守恒、循环和设备要求。最终交付文件须按对应
工作流进行精确文件复开运行核验，不能用另一个工作副本的结果替代。

设备类型初筛、手工估算、严格热工计算和机械设计验收也应分别标识。文件哈希
证明的是身份一致，不证明计算结论正确。

交付说明宜包含结论、文件清单、设计基准、主要计算依据、验收结果和待处理项。
项目使用者确认完成后，再进入方法整理阶段。

## 7. 方法整理与候选审查

任务进行中，记录必要的输入、修订、试算和结果，继续完成本项目的推导与优化。
用户明确确认当前任务版本结束后，才整理可复用的方法候选。

候选分为宏观原则和数据规律。宏观原则描述判断次序、设计取舍、适用边界及
验证方式；数据规律描述在明确条件下观察到的收敛、可行域或性能关系。两者
均需与现有方法比较，明确落点。没有可重复使用的增量时，保留项目记录即可。

数据比较使用相同设计基准、方法、目标、精度和版本，保留对照、反例及未参与
调参的测试。经检查的候选仍需人工审查后才能写入通用规则。任务特定的放宽
结果及其派生材料不作为共享规则依据。

普通来源资料增补不是任务经验进化。用户明确要求补充教材、标准或其他资料时，
可按来源、许可、单位基准和适用层级审查并建立独立候选知识版本，不必等待
资料维护任务结束；从当前任务表现中提炼跨任务规则，则仍须通过关闭与质量门。
两类输入均不直接覆盖活动库。格式、逐节点审查和受控构建命令见
[知识维护入口](../knowledge/MAINTENANCE.md)，日常查询见
[知识库说明](../knowledge/README.md)。

## 8. 调用示例

### 流程方案审查

> 读取工作区的设计任务书和物料表。先检查工艺顺序、组分去向、压力层级、
> 热量利用及循环结构，列出需要详细计算的项目，再确定建模工作流。

### 塔及热泵方案比较

> 以当前模型的处理量和产品规格为共同基准，审查塔的操作条件，比较常规供热
> 与适用的热泵替换方案。保留设备负荷、压缩功及各方案的验收结果。

### 设备可实现性检查

> 读取同一候选模型的设备负荷和物流导出，计算可确定的选型参数。区分能力
> 超限与资料缺失；需要调整时，说明方案及应返回流程复算的项目。

示例用于说明任务表达方式，不提供默认进料、设备尺寸或运行参数。

## 9. 可直接执行的离线调用

以下以第3节安装的路径为例。也可把`$chemRuntime`改为本产品的解压目录，
不需要安装或连接其他资料仓库。先选用已安装离线依赖的Python，再进入本产品目录：

```powershell
$chemPython = 'D:/ChemicalRuntime/python-env/Scripts/python.exe'
$chemRuntime = 'D:/ChemicalWork/chemical-engineering-runtime'
Set-Location -LiteralPath $chemRuntime
```

### 9.1 先发现能力与输入格式

```powershell
& $chemPython tools/expert_cli.py --describe
& $chemPython tools/expert_cli.py --schema expert-request
& $chemPython tools/expert_cli.py --schema process-feedback
& $chemPython tools/expert_cli.py --schema design-stage
& $chemPython tools/expert_cli.py --schema solve-route
& $chemPython tools/expert_cli.py --schema pressure-methods
```

`--describe`返回本产品的实际技能位置、知识范围、接口与后端策略。
`equipment_gateway.operations`是本地统一入口允许的操作；原后端能力表中另列的
Aspen导入和远程模型执行，不因此自动得到授权。需要更细的设备字段时，从能力
结果选择一个实际的schema ID，再传给同一个`--schema`入口，不凭设备名称猜ID。

### 9.2 先查思想和方法，再读取细节

```powershell
& $chemPython tools/expert_cli.py --query '预热 压缩' --corpus chemical_principles
& $chemPython tools/expert_cli.py --query '预热 压缩' --corpus chemical_principles --vector
& $chemPython tools/expert_cli.py --node-id L3-05 --corpus chemical_principles --full-text
& $chemPython tools/expert_cli.py --query 'GB/T 17395' --corpus equipment_standards
```

“预热 压缩”的思想入口是L3-05：先减少不必要负荷，再回收和匹配热量，最后
评估适用的温位提升。`--vector`使用随包哈希向量，不下载模型；普通查询不要求
NumPy。标准查询走本产品携带的设备标准事实库。命中后仍要检查来源版本、
单位、适用条件和证据等级，不把检索命中当作当前设备限值。

默认结果可为摘要。需要全文时用返回的`node_id`精确查询；细节任务可加
`--detail`下钻。正文待核或未随包时以返回状态为准，不把来源路径当成另一台
电脑上可以自动读取的文件。

### 9.3 计算给定工况下的设备参数

```powershell
& $chemPython tools/expert_cli.py --request examples/heat_exchanger_request.json
& $chemPython tools/expert_cli.py --request examples/parallel_pressure_request.json
```

合成换热输入规定Q=1000 kW、U=500 W/(m²·K)、对数平均温差40 K、F=1。
原设备程序换算负荷后得到`A=Q/(U·F·ΔTlm)=50 m²`，同时返回公式链、未闭合参数
和型式状态；这不等于完成EDR或机械设计。并联压力例中两支路在共同10 kPa压差
下分别通过20与10 m³/h，总流量30 m³/h；并联系统压差不是两支路压差之和。
这些输入都是软件核对用例，不是项目默认值。

### 9.4 生成可追溯的设备到流程反馈

下面的完整用例把同一工况、当前要求和一个明确合成的单机30 m²上限绑在一起。
它只演示“实际计算→适用约束比较→修改候选→复算清单”，不提供厂家能力证据。

输出的父目录须已存在，`synthetic-feedback-001`本身须不存在：

```powershell
$chemCase = 'D:/ChemicalWork/synthetic-feedback-001'
& $chemPython examples/prepare_feedback_case.py --output-dir $chemCase
```

生成器只准备输入，不运行设备程序。它返回`next_command`和等价的
`next_command_argv`；复制打印出的下一条命令即可执行。按以上路径设置，命令为：

```powershell
& $chemPython tools/expert_cli.py --request "$chemCase/feedback_request.json" --evidence-root $chemCase --output "$chemCase/feedback_result.json"
```

生成目录中的资料分别承担以下职责：

| 文件 | 用途及检查时机 |
| --- | --- |
| `source_export.json` | 显式合成的当前工况，不是假造Aspen导出；绑定case/run、设备族、输入值和单位。 |
| `authority.json` | 冻结本用例的方法和验收边界；开始计算前核对。 |
| `synthetic_single_unit_limit.json` | 30 m²合成上限、来源标识、版本和适用对象；绝不能当作真实设备上限使用。 |
| `constraint_review.json` | 将本次设备面积推导与上限文件的`/value`定位连接；请求通过`/constraints/0`引用此记录。 |
| `feedback_request.json` | 交给统一接口的完整请求，含实际设备参数、当前资料哈希、压力初筛及声明的连接关系。 |
| `case_manifest.json` | 列出输入身份、哈希与下一条命令；不含伪造的设备结果。 |
| `feedback_result.json` | 执行第二条命令后才产生，保留真实设备响应和反馈计划。 |

本例的结果应按层次读取，而不是只看一个成功标记：

- 实际面积为50 m²；与30 m²合成上限比较后，条件初筛下界为
  `ceil(50/30)=2`。`initial_count_bounds`给出该推导，`unit_count`仍为`null`。
- `preferred_route=exchanger_series`是待评审的串联分段候选，不能直接把50 m²
  平均分成两台。分段热状态、温差和U变化后，所需总面积仍可能改变。
- 另一个明确合成的单侧压力初筛执行`500000−20000−30000=450000 Pa`，即绝压
  500 kPa降至450 kPa；它没有计算第二侧压降，也不是EDR评级。
- `binding_gaps=[]`只证明本例输入与引用相符。受影响连接组件为
  `SYN-P1/SYN-E1/SYN-S1`，计划标记`STALE_UNTIL_REPLAYED`，表示采用候选后这些
  对象需要重算；断开的`SYN-DISCONNECTED`不属于该组件。
- `flowsheet_modified=false`、`engineering_accepted=false`和
  `automatic_aspen_mutation=false`保留原意：程序没有改动或运行任何Aspen模型。

资料被改而哈希未更新时，程序拒绝该引用；即使哈希正确，单位或适用对象错误
也不能支持拆分。仍可推导的面积应保留，缺口只阻断受影响结论。生成器拒绝复用
已有目录，结果文件也拒绝覆盖；重做试验请使用新的输出目录。

真实工程采用修改候选后，应按专业技能实施、重新导出同一模型并完成下游复算。
用`--schema process-replay-audit`查看回执入口；必须提供真实域检查记录，不能
给所有门填入自声明的`passed=true`，也不能把本例当作仿真验收回执。

### 9.5 连续请求与批量设备

统一接口支持JSONL：每行是一份完整专家请求，每行返回一份结果。下面把两份
现有例子压成单行后送入同一会话：

```powershell
$chemRequests = @('examples/heat_exchanger_request.json', 'examples/parallel_pressure_request.json')
$chemRequests | ForEach-Object {
    Get-Content -LiteralPath $_ -Raw -Encoding UTF8 | ConvertFrom-Json | ConvertTo-Json -Depth 100 -Compress
} | & $chemPython tools/expert_cli.py --session-jsonl
```

有设备请求时会话按需启动一个本地设备工作进程，顺序处理并复用已加载的库。
输入结束后关闭自有工作进程，不需要桌面程序常驻。引用项目文件的请求需另加
明确的`--evidence-root`。也可发送`operation=equipment_batch`，其中
`payload.requests`为原设备请求数组；结果逐项保留成功或失败，不用一台成功
代替整批验收。

### 9.6 在MCP宿主中使用同一套后台

本专家MCP以stdio提供9个工具。宿主用第3节建立的Python环境启动
`tools/expert_mcp.py`，例如以下启动项；具体外层配置格式由宿主决定：

```json
{
  "command": "D:/ChemicalRuntime/python-env/Scripts/python.exe",
  "args": ["-X", "utf8", "D:/ChemicalWork/chemical-engineering-runtime/tools/expert_mcp.py"]
}
```

| 工具 | 输入与作用 |
| --- | --- |
| `product_describe` | 不传`schema_id`时发现实际能力；传入ID时读取产品或设备输入契约。 |
| `design_stage_check` | `payload`使用`design-stage`字段，`evidence_root`指向当前资料目录；按阶段实际查询、计算并返回收据和未闭合项，不授予工程通过。 |
| `aspen_solve_route` | `payload`使用`solve-route`字段；按问题分类返回工具、时机、必读方法和证据待办，不启动Aspen、不批准外部替代。 |
| `knowledge_search` | 给出`query`或`node_id`之一，并按需指定`corpus/vector/detail/full_text`；返回知识及来源边界。 |
| `equipment_calculate` | `request`是原设备请求，不是外层`operation=equipment`封套；执行单次设备工作。 |
| `equipment_batch` | `requests`是原设备请求数组，同一工作进程顺序处理并保留逐项结果。 |
| `pressure_calculate` | `method`和`inputs`使用`pressure-methods`公开的名称与单位，返回声明模型下的计算。 |
| `process_feedback` | `payload`取完整反馈请求中的`payload`对象，`evidence_root`明确指定上述资料目录；返回候选和复算要求。 |
| `process_replay_audit` | `payload`含`plan/replay`，并提供`evidence_root`；核对同版模型及真实域检查证据。 |

使用顺序可沿用本章：发现能力、查方法、计算设备、读取反馈，再由专业工作流
完成真实模型复算。MCP不另建一套计算算法，也不自动授权流程改动。宿主结束
会话时关闭标准输入，后台释放自有工作进程。

原Aspen 70工具封装是单独的可选服务，入口为
`vendor/aspen-mcp-toolkit/run_offline_mcp.py`。其中真实Aspen操作仍需要本机软件、
许可和显式授权；不能因为专家工具可在无Aspen环境查询和计算，就认为该可选
服务的全部工具也不依赖Aspen。

### 9.7 按设计阶段主动调用

资料阶段可以直接运行这个查询示例，不要求编造尚不存在的设备输入：

```powershell
& $chemPython tools/expert_cli.py --request examples/source_stage_request.json
```

阶段入口先读系统层节点，再查询当前问题，并发现设备后台能力。后续阶段使用
当前来源及设备清单执行真实计算，字段由`--schema design-stage`给出。要观察
“岛内工况—设备计算—约束反馈—压力检查”的实际连接，可复用本包的合成输入：

```powershell
$chemStageCase = 'D:/ChemicalWork/synthetic-stage-001'
& $chemPython examples/prepare_design_stage_case.py --output-dir $chemStageCase --stage island
```

生成器沿用第9.4节相同的换热器输入和合成上限，不重新维护另一套公式。复制它
打印的`next_command`执行，才会产生`design_stage_result.json`。这个文件保留
实际查询节点、设备请求响应、当前来源身份、压力计算及需要继续完成的事项；
没有运行Aspen，也不会生成假的交付回执。

`MODULE_CHECKS_EXECUTED`只表示所列模块检查已执行，不表示设备清单完整或
工程通过；`ACTION_REQUIRED`还会说明哪些输入或检查未闭合。即使资料不齐，
已经能计算的设备仍返回结果。修改温压、负荷、相态或连接后，用新版本输入
重新调用，不能把旧收据的标签复制过去。最终的真实软件和工程检查仍按第6节执行。

### 9.8 在查数和调参之前选择工具

可以独立运行下面的工具分类示例，不需要模型路径或设备清单：

```powershell
& $chemPython tools/expert_cli.py --request examples/solve_route_request.json
```

本例要求“进料变化时自动补充溶剂，同时在产品约束下联合调参降低能耗”，对应
`live_relation` 和 `optimize` 两类意图。程序给出 Calculator 与约束优化的
实施顺序和待核事项，没有执行任何模型。只问当前值时用 `read_value`，一次
推导用 `derive_once`，匹配目标用 `match_target`；完整字段以
`--schema solve-route` 为准，不能给请求填“已通过”代替执行。

Agent 必须按意思理解任务，不依赖用户说出英文工具名。程序内的自然语言识别
仅覆盖有限触发，无法分类时要求 Agent 结合项目明确意图；不是通用语义模型。
阶段请求也可以带 `solve_request`，让同一个分类结果进入阶段收据。
