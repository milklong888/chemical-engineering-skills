# 0.4.6：让助手找到合适的方法，把结果核实清楚，让经验有处可用

一项复杂任务，通常需要助手连续做几件事：理解要求、查找依据、选择方法、调用工具，再把结果整理成交付物。我们把不同任务的操作说明、参考资料和配套脚本组织成 Skill，供助手在处理相应问题时读取。

但把这些内容放进一个库里，并不会自然形成完整的工作流程。一份 Skill 可以说明某项工作怎么做，却未必能让助手判断：当前任务该不该用它，材料不够时先查什么，什么时候需要另一项能力，以及完成后应把什么交回主任务。随着库的规模扩大，这些衔接问题也需要明确处理。

这轮更新围绕这些问题展开。相关调整已汇集到 0.4.6，涉及任务组织、资料读取、决策依据、执行记录和经验维护。它们作用于助手执行任务时读取的说明与使用的工具。

**先让助手知道，这次任务到底由谁负责。**

例如，用户只是要求核对一份已有报告。如果助手仅凭报告中的专业词汇选择方法，就可能进入重新设计或重新计算的流程；遇到多个相关 Skill 时，也可能分别完成一些局部工作，却遗漏最终交接。

为此，我们按交付目标重新整理了现有 19 项 Skill 的入口。每项入口都说明什么时候接手、需要什么输入、应交回什么结果、可以请求哪些协作，以及哪些相近任务不属于它的范围。主任务负责判断和整合，专门模块完成被委托的部分，随后把实际产物、依据和未解决的问题交回。

因此，处理“核对已有报告”时，助手有一条明确的审查入口；只有发现当前结论确实依赖新的计算，才沿协作关系进入相应方法。使用者可以直接描述想要的结果，助手则依据这些已写明的分工选择下一步。

**让每次读取围绕当前问题展开。**

如果每个入口都重复介绍整套流程，一条规则就可能出现多个副本。后续改了一处，其他地方仍保留旧说法；助手处理小问题时，也可能读入大量无关步骤。

这轮整理合并了重复的选择说明。总入口保留任务判断和必要约束，详细方法保留在负责该方法的模块中，通过引用按需读取。这里借鉴了技能组织研究中对能力分工、方法粒度和原始约束连接的讨论，具体落实为入口和引用的人工整理。对应关系可以在[研究采用说明](https://github.com/milklong888/chemical-engineering-skills/blob/main/plugins/chemical-engineering-skills/skills/chemical-engineering-expert/references/SKILL_RESEARCH_APPLICATION.md)中逐项核对。

对使用者而言，窄任务有了直接进入所需内容的路径；复杂任务可以沿协作关系逐步展开。对维护者而言，一条专业规则有明确的修改位置，相关入口通过引用使用它。

**资料不足时，把“下一步查什么”写出来。**

工作中常见的困难是：已有几种可选方法，但缺少决定该用哪一种的条件。如果说明只有“是”和“否”两个分支，未知信息就容易被当成某个已确定的答案。

我们为任务选择、工具使用、排错和经验维护补充了决策分支，保留“有依据成立”“有依据不成立”和“未知或冲突”三种状态。进入第三种状态后，助手应先获取能够区分分支的证据，再决定依赖该条件的步骤。

例如，复用一份已有结果之前，需要知道它对应的输入和版本。缺少版本信息时，应先查记录或读取相关文件；查不到，就保留这项缺口。这样，决策树说明了判断条件，也说明了判断暂时做不出来时如何继续。[决策规则](https://github.com/milklong888/chemical-engineering-skills/blob/main/plugins/chemical-engineering-skills/skills/chemical-engineering-expert/references/TASK_DECISION_TREES.md)

**把“改了哪里”和“拿到的是哪份结果”变成可检查的记录。**

规则调整之后，维护者还需要找到引用它的其他文件。任务做完之后，助手则需要确认交付结果对应的是当前输入，避免把同名旧文件当作本次成果。单靠一段总结，很难完成这两类核对。

本轮配套提供了两项本地工具。文件组织与影响索引读取库内文件和明确引用，给出某次修改可能影响的模块与复核路径。运行记录观察索引读取指定结果文件，核对文件指纹和指定身份字段，分别列出缺失、变化、冲突或尚未观察到的内容。

例如，一份方法说明修改后，可以先查哪些入口仍引用它，再逐项复核；准备交付一个结果文件时，可以核对它是否与记录中的文件一致。这些检查提供了具体的核对对象。计算是否成功、结论是否成立，仍要读取实际结果判断。[文件影响检查](https://github.com/milklong888/chemical-engineering-skills/blob/main/docs/skill_organization.md) · [运行记录检查](https://github.com/milklong888/chemical-engineering-skills/blob/main/docs/observation_index.md)

**让经验从一次任务中留下来，也让它保留适用条件。**

一项方法即使在当前任务中成功，下次也未必适用。如果只保存“这样做能解决问题”，输入条件、有效版本和失败边界都会丢失；如果把每次总结都追加到总说明里，重复或相互冲突的规则又会不断积累。

有关 Agent 自进化的研究为这部分维护提供了参考。[Reflexion](https://papers.neurips.cc/paper_files/paper/2023/hash/1b44b878bb782e6954cd888628510e90-Abstract-Conference.html)把任务反馈整理成后续尝试可以读取的文字反思；[ExpeL](https://arxiv.org/abs/2308.10144)从多次任务经历中提炼经验，在之后的任务中检索使用。它们提示了一条可行的改进方向：让执行经历形成带有依据、能够再次读取的材料。

在本库中，这个思路被接到已有的维护流程里。出现可复用成果时，助手先整理候选，写清遇到了什么问题、采取了什么方法、有什么实际证据，以及适用和不适用的条件。执行成功的方法要核对准确版本与结果；来自讨论的思想原则，则先确认具体内容，再由助手审核。代码提交或检查通过可以帮助核对记录，但不能单独证明经验成立。

候选先在本地核对证据、适用范围和已有重复；获得公开授权的摘要可以提交临时箱。等用户发起正式整理时，再系统检查它与当前规则的关系、冲突和反例，决定是否改动正式规则。已有规则能覆盖的，可以保留原文或补充证据；确有新内容的，再决定合并、细化、替换或新增，并记录修改位置、版本和回退依据。

[ACE](https://arxiv.org/abs/2510.04618)讨论了持续重写上下文可能丢失细节的问题，并采用结构化的增量更新维护经验。本库据此复核局部修改的方式：能修正一条具体规则，就在它原来的维护位置修改，保留来源和适用范围。这里维护的是助手可读取的规则与外部记忆，模型权重保持不变；这些研究也不能代替本库自身的效果验证。

**让普通使用者知道，值得保留的经验怎样提交。**

有了整理流程，还需要有人在合适的时候把候选提出来。因此，全部 19 项 Skill 已接入阶段收尾提醒：出现有复用价值的新成果时，要求主助手展示具体摘要、适用条件和投稿入口。多个协作助手发现的候选，统一交给主助手整理。

使用者核对拟公开的摘要并授权公开后，可以通过[公开经验收件库](https://github.com/milklong888/chemical-engineering-experience-inbox)提交 PR。提交步骤见[中文投稿指南](https://github.com/milklong888/chemical-engineering-experience-inbox/blob/main/docs/USER_SUBMISSION_GUIDE.zh-CN.md)。临时收件保留了可供后续审核的材料，正式采用仍需单独审查。

这些改造已经提供了任务导航、查询分支、核对工具和经验整理入口。助手是否在具体任务中及时读取并正确使用它们，还需要根据实际调用和交付结果检验，不能仅凭规则已经写入就认定每次都会触发。
