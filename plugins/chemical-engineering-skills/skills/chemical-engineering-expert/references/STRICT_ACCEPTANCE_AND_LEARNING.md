# 严格标准、当前任务放宽与学习隔离

本文件规定发行版的工程验收与方法候选资格，不替代专业公式、当前项目目标或
实际软件证据。所有被要求的错误和警告计数须为零。

## 1. 严格默认，不混淆任务阶段

- 在工作开始冻结适用标准ID/版本/来源哈希、阶段、必需门、基准、容差和验收证据。
- 操作完成、可读结果、初步估算、局部修复、求解干净、产品达标、正式交付是不同状态。
- `strict_passed`只由该阶段完整证据成立；未测、未知、缺失均不是通过。
- 初步设计中的有据估算可以标为`J/provisional`继续工作，但不冒充正式验证；读取结果不需要先完成整厂验收。这种正确限定阶段不是放宽。
- 较新来源纠正旧公式/单位/表头，需记录来源与回归，是规则纠错；不能借此降低实际验收要求。
- 旧证据是否可复用按下方文件范围分支判断；证据身份和工程通过分别核查。

### 可验证范围与局部缺口

按当前证据能确定的事项逐项确认，不要求为一个局部结论逐行浏览所有无关进度信息。先核运行/文件身份和与该结论有关的消息及上下文；仅当声称“整次运行无问题”时，才需要完整捕获、结束证据及全程问题扫描。未捕获完整消息不能写成整次无错。

完整原生Summary没有取得时，记录“汇总计数未知”；这不等于软件实际报错，也不抹掉独立成立的输入、连接、产品或文件结论。继续完成可独立核实的工作，列出已核实、失败、未知和不适用及理由。相同取证路径没有新信息时，保留缺口与下一依赖，不无限重试、不让整个任务中停。

缺表不能生成零值，也不能授予全零计数或整体`strict_passed`。当前合同明确要求完整计数表时，该项仍未完成；真实报错、可辨非零、身份冲突和被污染的结果必须处理。局部证据足够不代表所有结论都可以成立，也不是接受错误的豁免。

逐项判断依赖：产品检查可与Summary核查独立推进，但所用结果须证明属于当前候选、已完成相应计算且相关上游状态有效；缺这些证据则该产品结论也未知。局部界面/锁屏不可用时继续可用的受控读取和导出，界面项目单列待核。交付已有核实的资产时准确标明范围，不把它叫整体验收通过。

来源定位：经验候选`EXP-20261017-verifiable-acceptance-and-closure / P0-016、P0-019`（PR #3，固定提交`2a1d8ae00d1f2266268bf6d71f9b834bda45844f`），本次按用户2026-10-26明确要求合并。EXP-ID与子条ID共同定位，不能与另一来源同名P0-016混用。

### 文件范围与证据复用

先辨认旧回执验证的是模型、运行依赖、说明文稿还是整个交付包。逐项比较当前
模型及依赖（如 EDR、子程序、Calculator、输入脚本和外部数据）的内容身份与
变化记录，再判断受影响范围。文件名、修改时间和外包哈希不能替代该比较。

| 实际核对结果 | 可以保留什么 | 还需完成什么 |
| --- | --- | --- |
| 只改包装或说明；模型及完整运行依赖已证明相同 | 原资产在原工况、版本和原路径下已验证的范围 | 审查新增说明与结果一致；新交付路径按原交付规则核验，不继承整包通过 |
| 模型、运行依赖或会改变使用方式的说明发生实质变化 | 已证明不受影响的既有证据 | 按影响链重算和复核受影响资产，再验证当前交付 |
| 只有同名、时间或总体哈希，缺逐资产证据 | 旧回执继续作为原对象的历史记录 | 当前能否复用仍未知；列明需要的内容比较与依赖清单，不能把未知说成已变或未变 |

即使本次拿不到文件，也要说明上述条件分支；不要只回答“整包哈希不同所以全部
作废”，或“同名所以可继承”。哈希相同仅证明所比较字节相同，工程结论仍须有
原始有效回执及适用范围。精确新路径的复开要求归
[操作层交付规则](../../aspen-plus-operations/SKILL.md#strict-handoff)，并未取消。

## 2. Aspen运行状态检查

本节定义“完整汇总计数全零”和严格模拟通过所需证据，不是开始其他独立核查的前置条件；缺口按上方[可验证范围](#可验证范围与局部缺口)报告。四类行保持：Terminal Errors、Severe Errors、Errors、Warnings。
列来自经核实的版本/格式表头。只有全部命名单元完整且为零才能称该表全零；缺行、少列、未知格式或矛盾多表均不能补零。成功短语不生成计数，不覆盖真实报错。

Aspen默认及当前模型已有的求解容差属于冻结输入。保留基线数值和默认/显式卡状态，不能为了收敛而收紧、放宽、新增或删除全局、tear/recycle、塔、flash、衡算及已有Design Spec容差。新建Design Spec的来源明确目标容差另作规格记录，不借它掩盖未收敛。既有容差锁由操作owner核基线与最终同版本导出；缺比较证据则该项未知。

当前支持的原生结构为`Physical Property`、`System`、`Simulation`三列，Physical Property可折行。其他结构须有实际来源与明确解析配置，不能把缺列解释为较小合法表。

严格模拟通过还要求当前运行完成，输入/导出/日志身份一致，同次Control Panel实际消息与原始`.his`完整捕获且可解释解码，全程无实际错误或警告，汇总与历史无矛盾。Required Input、块状态、产品、守恒、设备和精确交付文件复开分别核验；它们不能互相抵消或由保存、Run2返回、BLKSTAT=0替代。

格式证据见[运行错误汇总表格式](../../aspen-plus-operations/references/summary_format_contract.md)。解析实现仍唯一归属`aspen-plus-operations/scripts/aspen_evidence.py`及真实调用者。本次范围规则不修改其未知/失败输出，也不把解析器失败状态直接解释成物理软件故障。

## 3. 用户可放宽当前任务，但不能伪造严格通过

用户须明确指明当前任务、放宽的规则/指标、范围和期限。口头“先做出来”、
附件作者的客户偏好、历史项目允许、代理自行解释都不构成新放宽授权。

放宽前写入项目变更表/`ACCEPTANCE_OVERRIDE.json`：原标准、原阈值/门、
用户原意引用及消息定位、具体改变、理由、未通过的严格项、风险、当前候选
身份、有效范围和`learning_eligible=false`。不改中央默认标准。

放宽交付只可标`case_accepted_with_relaxation`或`diagnostic_only`；保留原始
错误/警告和未测项，不标strict_passed。物理事实、证据真实性、法律和安全
义务不能被放宽；禁止日志删改、虚假软件身份、用外部结果冒充Aspen原生求解。

## 4. 放宽来源链永久禁止自进化

只要本任务或任一祖先使用放宽标准，其模型、日志、参数、图、报告、总结、
修复轨迹、成功标签、错误记忆候选和后续派生内容全部继承：

`learning_eligible=false; success_case_eligible=false; default_rule_eligible=false;
default_retrieval_eligible=false; provenance_state=relaxed_lineage`

仅存当前项目审计/追溯，不能进入通用Skill、共享知识图谱、正例库、训练/
自进化样本、偏好权重或默认RAG。人工说“本次算完成”、重新命名、复制、
摘要或复跑同一放宽来源，都不洗掉隔离标签。

允许用独立、不依赖该放宽链的严格来源重新验证同一一般机制；新证据另立
身份和谱系，不能把旧放宽产物迁为严格正例。中央只记录“不得从放宽学习”的
治理错误，不把具体放宽内容反向写进全局错误记忆。

## 5. 新晋升、旧事件与执行门

正式经验晋升有先决时机门：用户明确发起周期整理，且当前task/revision已确认
结束，才按EVOLUTION_LOOP.md启动晋升审查。微调期间继续项目审计与当前求解。
明确授权的临时经验收件另按[收件导航](EXPERIENCE_INBOX.md)检查成功作用范围、
内容身份、谱系和发布范围，可早于任务结束，但不进入正式Skill、图谱或默认RAG。
第4节的放宽隔离同样适用于临时共享候选。用户明确要求修改机制属于直接维护。

- 新技术/代码机制晋升前运行`../scripts/evaluate_learning_eligibility.py`，校验完整来源谱系、有效标准、严格结果和证据文件哈希。通过仅表示可进入人工候选审查，不自动授权写入canonical。
- 新工程规则还需来源、单位/适用域、独立技术核验、反例、当前版本、人工批准及回退证据。模型自评或测试自己的固定措辞不够。
- 旧`verified/accepted`标签不自动证明满足本次严格标准；有冲突或无法核验的遗留事件保留原文，effective状态为`legacy_unassessed`/historical，默认检索与晋升关闭。
- 用户要求的代码缺陷修复/规则纠错是显式维护，不是从放宽运行学习；仍要测试和保留变更链，不能声称未跑软件已经动态验证。
- 不删除历史证据；只维护唯一owner及其生成镜像。恢复/压缩上下文后仍先读取当前严格合同和本任务override状态。
