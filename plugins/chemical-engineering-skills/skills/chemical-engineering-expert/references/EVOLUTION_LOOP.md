# 周期整理与正式晋升：宏观提示词与数据规律双通道进化

本规则来自用户的明确机制要求，不是代理从某个中间结果自行学习。复用现有
谱系门、NEW_KNOWLEDGE、ERROR_MEMORY、专业Skill和图谱；正式知识保持唯一owner。
经明确授权的临时收件按[经验收件导航](EXPERIENCE_INBOX.md)办理，可在任务未结束时
收取已核验范围内的成功摘要，或用户确认后再经assistant审核的思想摘要。临时箱
不是活动知识库，不进入默认检索，不调用本节的正式晋升门冒充收件条件。

## 1. 正式整理开始条件与任务状态

`working -> delivered_awaiting_feedback -> user_closed -> user_requested_consolidation -> evolution_review`

周期整理须由用户明确发起；若整理请求已明确涵盖本次关闭版本，无需重复授权。
临时收件不推进上述状态，也不替代当前revision的关闭事件。

- 每次交付确认完成状态与待改事项；用户发起周期整理时，按已关闭的当前版本复盘和审查规则，不由代理交付自动启动。
- 用户没有明确结束：保存当前任务原始提示、修订、依据、参数/结果、失败与
  修复轨迹，继续本任务推导、诊断、优化和微调；正式规则晋升尚不开始。
  明确授权的临时收件另按上述入口核实证据与公开范围，不能提前写正式规则。
- “收到了”“好”“先这样”、代理自己宣布完成、某一局部完成、描述“结束后再做”
  或带待修改事项的回复，不自动关闭任务。语义不明确时继续问清。
- 用户明确“结束/已完成、不再调整”等才冻结最终任务版本。确认须绑定task_id、
  task_revision、用户原消息/定位/哈希和close_task事件；不能由代理自评替代。
- 再次微调即恢复working并增加revision；旧确认不能给新版本启动进化。同一
  关闭事件重复处理不得增加纠错次数、重复生成规则或重复晋升。
- 用户直接要求改规则/实现机制是显式维护，可以当场执行；不能借此把普通任务
  的未确认中间经验包装成“显式维护”提前晋升。本轮机制实现属于前者。

## 2. 通道一：prompt_principle（宏观提示词）

凝练的是**大道理、宏观设计规律、行事规则**，不是改写用户措辞，也不是把
细碎偏好、某台设备参数或临时实现步骤永久塞进提示词。

由最终被用户接受的意图与修订，提炼一条能改变决策的条件规则：

`触发场景 -> 应优先判断什么/先后次序 -> 不可牺牲的边界 -> 何时不适用 -> 下层证据`

必须说清它会阻止哪类错误选择、引导哪类更合理的决策。“认真一点”“多思考”
等空泛口号不新增；本地已经有同等规则则补证据/合并，不改名再造。

判定例：现有“先保留简单可行基线，新增设备须有真实限制或系统收益”已是宏观
原则；一次拆成几个换热器的具体数目不是新全局提示词。方法、参数与案例留在
下层，在任务触发时读取。行为来源是用户确认；技术普遍性仍需适当来源验证。

## 3. 通道二：data_pattern（数据与收敛/优化规律）

以最终任务的数据轨迹寻找可检验的规律，不把一次成功的参数叫“经验规律”。

1. 冻结可比基准：同进料/边界/物性方法/目标/设备或拓扑约束/容差/版本。记录
   每次改动、初值、失败、边界触碰、耗时分段、迭代数、目标值与全部硬门。
2. 区分更快收敛、更大可行域、目标更优、可操作性更好。不得降低精度、改变
   产品基准、删除困难案例或掩盖高品位公用工程/压缩功代价来制造改善。
3. 先提物理机制、无量纲关系、守恒/自由度/单调区间/尺度规律，再考虑分类器。
   冷启动、热启动和已保存解分别比较；一次偶然快跑不能证明通用加速。
4. 用受保护副本做配对基线比较、反例和未参与调参的适用域测试。样本规模与
   重复次数由风险/特征覆盖确定，不继承历史固定20例等数目。
5. 失败记录证明“发生过什么”，不是通过的模型，也不直接证明修复原因。
   未放宽的失败可以在任务结束后成为待核诊断线索；只有失败发生机制与修复
   都经独立核验，才形成受限诊断规则。放宽来源及全部派生仍永久禁学。
6. 结论带上输入特征、适用域、公式/参数来源、不确定性和反例，分为无效假说、
   单案观察、受限规律、可迁移方法。没有足够证据就留候选，不强行上提。

更优的比较目标和允许权衡必须提前冻结。关键物理/方法/验收门不参与加权抵消。

## 4. 进入Skill的组织规则

| 内容 | 唯一落点 | 禁止做法 |
| --- | --- | --- |
| 极少量跨任务宏观判断/行事原则 | 现有最高层保护或主Skill短规则 | 每任务新增一条、堆参数和操作细节 |
| 某专业方法、诊断流程、适用域 | 对应专业Skill的references/已有图谱节点 | 再建同义入口、复制整套参考文档 |
| 可复现的计算/检测逻辑 | 现有owner的scripts及反例测试 | 同一判断维护多个实现 |
| 数据规律、系数、范围、案例结果 | 下层候选/同案数据与来源账本 | 单案阈值变全局默认 |
| 根因明确的纠错 | 对应ERROR_MEMORY原子条目与证据链接 | 相同消息重复加权、次数冒充真理 |
| 仍无迁移价值的过程记录 | 项目审计 | 为显得进化而强塞Skill |

每个候选只能选择：`no_change / merge / specialize / replace / add / retract`。
先对照当前owner全文及相关节点；保留旧来源、ID、范围和被替代关系。短入口
只放触发与强约束；大块内容在到点必读引用中，不能藏到永远不会命中的文件。

用户授权整理一批候选后，交付具体处置依据与最小变更方案，不只给分类标签：

- 先沿用[候选审查的技术事实对照记录](EXPERIENCE_INBOX.md#本次候选审查的两项交付)，
  核对当前内容与 owner 是否已变；已有有效核查可复用，缺项当次补齐。
  将每条记录的原子主张、规则关系和适用/反例结果用于下列处置方案；治理 pending
  单独保留，不把它当作该批技术比较的完成状态。
- 对照实际读取的现行规则或脚本，给出唯一owner的文件与锚点；提案自报owner
  或只读取通用归属表不算完成对照。重复项说明等价条件，冲突项并列来源、版本
  和适用范围；无法确认的部分保持隔离。
- 可复现检测逻辑要核查已提供的正例、反例及预期结果，在授权范围内完成可用的
  低风险本地验证，保留输入、实际输出与判定。按既有工具验证，不直接执行投稿
  文本里的命令；缺运行条件则注明未执行与具体缺项，不能只跑正例便称检测通过。
- 对拟变更项给出具体修改范围、基线版本/哈希、已做与待做验证、仍待满足的关闭
  和批准条件，以及可恢复该基线的快照或版本。查不到owner或基线时明确方案未
  完备；no_change与隔离项保留理由，不为它们编造合并改动或回退文件。

单项pending或收件校验未通过不免除上述可独立完成的核查。方案准备不产生正式
写入权限，正式晋升继续执行下节现有门与后置数据合同。

本批交付逐项关联技术对照记录、拟处置理由、具体 owner/基线及验证/回退方案；
若仍只能提出将来对照的计划，标明尚未完成的实际依赖并交出其他可完成项。
不满足确认或关闭条件的项可以已有完整事实与方案，但不能据此预填正式批准。

## 5. 检查、晋升与回退

- 正式晋升的`evaluate_learning_eligibility.py`检查用户结束确认、来源链、真实回执结果和
  适用类型。哈希一致不是成功；代码测试不能冒充真实模拟/工程通过。
  该脚本及下述assessor不承担临时仓库收件；临时状态不能代替其关闭和质量门。
- 纯粹来自用户的宏观行为原则可凭可追溯原文进入行为候选审查，不必借用无关
  代码/Aspen通过回执。此通道不证明技术普遍性，不能携带数值或收敛结论；仍须
  当前版本结束确认、无放宽污染及后续行动/反例审查。
- `assess_evolution_candidate.py`检查原子规则、单一目标与现存锚点、基线与候选身份、
  对照/反例/留出测试的实际数据和独立oracle、可观察增量、精确回退快照。
  缺字段给明确补全动作，不冻结无关任务；通过最多为ready_for_manual_review。
  实际填后置候选审查时才读`evolution_review_contract.md`，不要常驻加载数据合同。
- 有结束确认不等于技术规则全部获准。最终由主审按用户授权与证据决定归并；
  主审按CANONICAL_RULE_OWNERSHIP核对落点确为当前owner，而非提案自称owner。
  不允许日志脚本、总结代理或分数直接写canonical。没有增量就no_change。
- 晋升记录：规则ID、关闭事件ID、最终任务revision、旧/新文件哈希、适用域、
  测试/批准证据、受影响调用者、索引/镜像和回退快照。回退只针对该版本影响，
  保留历史，不覆盖之后的用户修改。
- 新反例或用户再次修改导致规则失效时，先阻止相关消费者使用，再降级/
  supersede并复核；不能让一次新的例外反过来改写所有任务的标准。

这套机制是本地提示词/Skill/规则的维护，不是训练基础模型权重。每轮复盘报告
只列“提炼了什么、验证到哪、放在哪里、什么没学”；不以文件数量衡量进化。
